# 平台适配特殊处理（坑位清单）

每条只写「是什么 + 根因 + 移除条件 + 详见何处」，不超过 3 行；细节放对应源码注释或 `docs/` 里。

- **国内 Nix 镜像暂只保留 USTC（清华源暂时移除）**：`modules/shared/nix.nix` 的 `substituters` 删除 `mirrors.tuna.tsinghua.edu.cn`，`modules/nixos/networking/proxy.nix` 的 `no_proxy` 同步删行；若身处境外，下载速度会偏慢，可自行更换镜像。**移除条件**：清华源恢复后按序加回（排在 USTC 之后）。
- **候选窗九宫格竖切线上的 1px 线**（**2026-10-22 已定位并修复**）：niri scale `1.5` 下候选窗右侧竖切线恒有 1 根欠覆盖的设备像素（卡片白 217、该列 177-182，亮度随背后窗口变 ⇒ 是漏底不是灰线；横切线干净）。**真凶是 GTK im module 的 client-side popover**——GTK4 应用（ghostty 等）在 `GTK_IM_MODULE=fcitx` 下由**应用进程自己**用 `gtk3/fcitxtheme.cpp` 的 `Theme::paint` 拼九宫格画候选窗，与 classicui / msime 插件无关（冻结应用进程画面即静止、`--disable classicui` 后 classicui 侧探针全零命中，均已实测）。**根因**：GTK 先把整块 paint 录制进 cairo recording surface（`gtk_snapshot_append_cairo`），1.5 倍缩放发生在回放阶段，录制上下文里 CTM 是单位阵、`device_scale=1.0`，所以「在 paint 里读缩放再按设备像素量化切线」拿不到真值（该方案已实现并真机实测无效，勿再走）。**修复**：`pkgs/fcitx5-gtk/nine-slice-overlap.patch`（经 `overlays/default.nix` 的 `fcitx5-gtk` override 生效）让相邻瓦片沿共享切线**重叠 1 逻辑像素** + `CAIRO_EXTEND_PAD`，不依赖读取缩放；九片改在 `cairo_push_group` 内用 `CAIRO_OPERATOR_SOURCE` 绘制、`alpha` 最后整体应用一次（否则半透明的高亮美术在重叠处叠两次 alpha 会出现 3 列亮带，复刻实测 102→153）。真机 A/B（同一批 10 组输入，仓库自建产物对照）：未打补丁 7/7 出缝（lum 169-170、`offR=9`），打补丁 **0/8** 出缝，且高亮行切口列回到与邻列同值（195 vs 175）；忠实复刻（recording + 1.5x 回放）50/100 宽度出缝 → **0/100**。**移除条件（2026-10-25 已执行）**：上游拒收等价修法（[PR #44](https://github.com/fcitx/fcitx5-gtk/pull/44)）；全局 `GTK_IM_MODULE` 移除后 Wayland 应用走 text-input-v3/classicui，ghostty/XIM 兜底等项手测通过，补丁与 fcitx5-gtk overlay 已删（X11 下 fcitx5-gtk 走 classicui-XCBUI 不经 popover 代码；若重新启用该路径需恢复补丁）。菜单窗（`[Menu/Background]`）走 `Theme::paint` 的 overlay 分支，本补丁只覆盖背景/高亮/箭头四类九宫格。
- **msime 0.13.0 的 notice 两表错位**（2026-10-22 定位，**2026-10-25 已随上游修复移除**）：上游 #9248 给 `MSIME_NOTICE_NAMES` 加了 `rime-wanxiang-CC-BY-4.0.txt` 却漏加 `MSIME_NOTICE_SOURCES`，`ZIP_LISTS` 装许可文件时整体错位一格，`frontend-npm-NOTICES.txt` 装不出来 → `msime-fcitx5` 的 `installCheckPhase` 断言失败；曾以 `pkgs/msime-fcitx5/notice-lists-alignment.patch`（经 `modules/nixos/core/default.nix` 的 overrideAttrs）补回对齐。**已移除**：上游已在 `platforms/linux/CMakeLists.txt` 自行补齐（msime master 2026-10-25），旧补丁反而造成 28/27 错位，补丁与目录已删。
- **msime 引用 fileset 白名单外的根目录文件（截至 0.16.0 仍存在）**（2026-10-25）：上游 2026-10-24/25 的提交让 crates 与 `packages/ui` 引用根目录的 `plugins/phrase_table/latex-symbols/symbols.tsv`（`engine/symbol_groups.rs` 的 `include_str!`，c289dd69）与 `resources/keyboard-skin-presets.json`（`packages/ui` 皮肤预设，da0e42f7），而 `platforms/linux/nix` 的 fileset 白名单没收录它们——GitHub 源码树里文件在、构建树里没有 → cargo 报 `include_str!` 找不到、vite 报 `Module not found`，拖垮 `msime-desktop` 与 `msime-fcitx5`。**现状**：`modules/nixos/core/default.nix` 用 `msimeLibFixed = prev.lib.extend` 给 `fileset.toSource` 包一层，把两个根目录文件 `unions` 进白名单，再经 `.override { lib = msimeLibFixed; }` 作用于 `msime-desktop`（`settingsWindow`）/ `msime-host-api` / `msime-mcp`（`msime-fcitx5` 自身 src 不缺文件，不动）。**移除条件**：上游修好 fileset 白名单后删 `msimeLibFixed` 段落（多并的文件对修好的上游是幂等的）。
- **NVIDIA 显存泄漏修复**：`modules/nixos/hardware/nvidia-base.nix` 配置 Niri 应用专属参数，限制空闲缓冲区池大小，规避显存泄漏问题。
- **NVIDIA 的 EGL 拿不到硬件加速（2026-10-28 定位并修复）**：EGL（GTK4 / Qt5 / WebKit 走的路）一直落到 Mesa 的 swrast 软件渲染，而 GLX 与 Vulkan 都正常拿到 NVIDIA——因为 NVIDIA 的 Wayland/X11/GBM 平台不是 glvnd 内置支持的，须由 `egl_external_platform.d/*.json` 声明，而 glvnd 只编译进了 `egl_vendor.d` 的默认路径、外部平台目录**没有默认值**，不指路就永远不加载；`__GLX_VENDOR_LIBRARY_NAME=nvidia` 只管 GLX，对 EGL 无效。**修复**：`nvidia-base.nix` 设 `__EGL_EXTERNAL_PLATFORM_CONFIG_DIRS=/run/opengl-driver/share/egl/egl_external_platform.d`（外部平台目录）与 `EGL_PLATFORM=wayland`（glvnd 的 `EGL_DEFAULT_DISPLAY` 会先落到 Mesa，须显式指定平台），二者缺一不可；真机 A/B：GTK4 应用 `GL_RENDERER` 从 `llvmpipe (Mesa)` 变为 `NVIDIA GeForce RTX 3060 Ti`，MyGo 云音乐启动日志不再有 `OpenGL draws on the CPU (llvmpipe)`。**移除条件**：glvnd 为外部平台编入默认搜索路径，或 nixpkgs 提供对应 NixOS 选项后。
- **显示器冷启动 EDID 自愈**：两块外接屏（4K 的 DP-3 / 24" 1080p 的 DP-2）长时间断电再上电时，NVIDIA 在 HPD 边沿立刻读 EDID，而该屏是「DP 接收端先起（1~3s 就拉高 HPD）、scaler/EDID 后起」，于是只读到合成 stub（`Nvidia 0x0000 Unknown`，模式列表只剩 640x480，叠加 scale 1.5 后逻辑 426x320）。stub 校验和有效且连接器仍 connected，RM 把显示对象连同 stub 一起缓存，只有**新的 HPD 边沿**或驱动重载才重建——`echo detect > status` 只刷新内核侧缓存，2026-09-26 实测 detect 每 2s 打满 10 分钟 + 两轮 force=off（链路真断）重训仍拿不回真 EDID，因此旧版 detect 自愈不可能生效；该屏还会拒绝 DDC/CI 软关机（VCP D6=0x04 → DDCRC_VERIFY，HPD 不撤销），所以也没法靠 DDC 逼它重初始化。`hosts/desktop/edid-reprobe.nix` 改为：检出 stub 且显示器 DDC 已就绪后，把本屏完整 EDID（`hosts/desktop/edid/icd-gx288ur.bin`，含 DisplayID 3840x2160@150）写进连接器 debugfs 的 `edid_override`——内核 7.2 起 override 不再让 probe 跳过 detect，nvidia-drm 每次 detect 都会把 override 交给 RM，连接器状态仍按真实 HPD 汇报，显示器断电即撤销 override。`drm.edid_firmware`/`video=` 已排除（冷启动时会把 4K 模式塞给尚未就绪的面板 → 黑屏）。**2026-10-31 扩到两块屏**：24" 屏（HWV SSN-24，DP-2）早上开机同样出 stub（此前自愈只认 DP-3，故一直停在 640x480，`niri msg outputs` 里身份是 `Nvidia 0x0000 Unknown`、唯一模式 640x480）；它的真 EDID 在内核侧已塌陷时仍可从 I2C 直读（`/dev/i2c-8` 的 0x50），存为 `hosts/desktop/edid/hwv-ssn-24.bin`（256 字节，base + CTA-861），模块已改为按 `panels` 列表逐屏自愈。完整根因与实测记录见该文件头部注释。**2026-11-15 自愈再次失效**：ddcutil 3.x 默认动态睡眠，启动时要按 `$HOME/.cache/ddcutil` 定位统计文件，而 `edid-reprobe` 是系统单元、无 `HOME`，`ddcutil detect` 直接 rc=1 且无输出 → 就绪判定永不成立；脚本的 detect 调用已加 `--disable-dynamic-sleep`。
- **WinApps（Windows 应用接入桌面）**：libvirt 后端，接入层 `modules/home-manager/gui/desktop/linux/winapps.nix`，装机盘 `pkgs/windows-vm-media`（xorriso 往上游 ISO 追加，不重打包）。**密码不进 nix store**：`RDP_ASKPASS` 读本机 `~/.config/winapps/rdp-pass`（0600）。探针走 libvirt `<hostdev>` 直通而非 RDP，模块提供 `winapps-usb attach/detach <vid:pid>`「谁用谁拿」。**完整手册见 `docs/winapps.md`**。
  - 两个已知坑：本地化 Windows 上 RDP 放行必须走 `WINAPPS-SETUP.bat`（上游按英文组名放行在中文系统必然失败）；直通期间设备**仍出现在 `lsusb` 里**，别拿它判断归属，看 `/dev/ttyUSB*` 或 `winapps-usb`。
- **Windows 客户机从 SATA 切 virtio 后进 WinRE（viostor 的 StartOverride）**（2026-11-21）：PnP 装 virtio 驱动时会给 `viostor` 写 `StartOverride=3`（按需启动），**覆盖** `Start=0`，引导时不加载驱动 → `INACCESSIBLE_BOOT_DEVICE` → 自动修复（现象：蓝屏「选择键盘布局」、`dir C:\` 报找不到路径）。**现状**：WinRE 命令行里 `drvload E:\viostor\w11\amd64\viostor.inf` 挂出系统盘后，`reg load`/`reg delete …\viostor\StartOverride` 并确认 `viostor.sys` 已在 `System32\drivers`；完整步骤见 `docs/winapps.md` §4.1。**移除条件**：virtio-win 安装器不再创建该覆盖值时。
- **nixpkgs 移除了 flclash（2026-08-17）**：nixpkgs 26.05 分支还留着 flclash 0.8.92，master 以「用户少 + 无人维护」为由移除并留了 throw 墓碑；本仓库的 nixpkgs 跟 master，故 `pkgs.flclash` 曾不可用。烂掉的是 nixpkgs 那份源码打包（每个上游版本要同步 `pubspec.lock.json` / `git-hashes.json` / core `vendorHash` 三份钉子），软件本身上游仍在活跃开发（2026-10-24 发了 v0.9.2）。**现状**：`pkgs/flclash/` 改用上游预编译 deb 自维护，属性名与 nixpkgs 的墓碑同名、由 overlay 盖掉。**移除条件**：上游或 nixpkgs 重新收录可用的 `flclash` 后。**限制**：TUN 模式依赖 `FlClashHelperService` 提权（上游给 setuid root），Nix store 不允许 setuid，故只剩「系统代理」模式（仓库的客户机透明转发走 redsocks + mihomo，不依赖 TUN）。**现状**：2026-10-28 起本仓库的代理客户端已从 `clash-verge-rev` 换成 FlClash（两者端口布局相同，见 `docs/packages.md`）。详见 `docs/packages.md`。
- **FlClash 自带的「开机自启」会写死绝对 store 路径**（2026-10-28 实测）：设置里的 `autoLaunch`（应用状态，存在 `~/.local/share/com.follow.clash/shared_preferences.json`）为真时，FlClash 启动会自己写一份 `~/.config/autostart/FlClash.desktop`，`Exec=` 是当时的**绝对 store 路径**（`/nix/store/…-flclash-<版本>/libexec/flclash/FlClash`）——与 magpie、clash-verge 同一个坑：包升级后旧 store 路径被 GC，条目静默失效。**现状**：自启改由 `modules/home-manager/gui/apps/linux/media.nix` 的 `xdg.autostart.entries` 声明（`Exec=FlClash`，走 PATH 恒指当前版本），应用内那个 `autoLaunch` 开关须保持关闭，否则两份条目会各拉起一个实例。**移除条件**：上游改为写相对路径或提供关闭自注册的开关后。
- **客户机使用宿主代理**：mihomo 只监听 `127.0.0.1`。默认走 `mySystem.proxy.transparentForVms`（desktop/laptop 已开）：`modules/nixos/networking/proxy-vm.nix` 在 virbr0 上把 TCP REDIRECT 给 redsocks、把 DNS 改投 mihomo 的 1053，客户机零配置；另有 `exposeToVms` 的 socat 转发（`192.168.122.1:<port>`）供客户机手动配置代理，二者可并存。不必开 Clash 的 allow-lan，也不用 route_localnet + nftables DNAT 那套（会把回环地址变成可路由地址）。详见 `docs/winapps.md` §10.4。
- **Noctalia 窗口截图在 niri 上不可用**（2026-11-09）：`noctalia msg screenshot-window` 要求合成器支持 `ext-image-copy-capture-v1` 与 `ext-foreign-toplevel-image-capture-source-manager-v1`，niri 26.04 两者都没实现（实测报 "window capture is not available on this compositor"；niri 二进制里也 grep 不到这两个协议）。**现状**：`Mod+Shift+P` 走 `niri-screenshot-window`（`niri/default.nix`），先用 niri 自带 `screenshot-window` 截到临时文件再交给 Noctalia 标注器。**移除条件**：niri 实现上述两个协议后，改回 `noctalia msg screenshot-window`。
- **自动升级固定走 flake**：`system.autoUpgrade.flake` 由 `networking.hostName` 推导出 `<primaryUser home>/Projects/nixos-config#<host>`（用户名经 `mySystem.primaryUser` 派生，不硬编码）。新增主机时 `networking.hostName` 必须与 flake 输出属性同名，否则 autoUpgrade 会找错目标。`allowReboot = false` 意味着内核更新后**不会自动重启**，需手动重启才能用上新内核。各主机的 flake 仓库统一位于 `~/Projects/nixos-config`，若某主机仓库路径不同需覆盖该选项。
- **滚动升级的可追溯性**：`--refresh` 每周重写工作区的 `flake.lock`，而 Nix 对脏 git 树令 `self.rev = null`，`system.configurationRevision`（`flake.nix` 中显式声明）会退化为 `"dirty"`，代际就无法回溯 commit。因此 `nixos-upgrade.service` 的 `postStop` 在升级成功后以本人身份提交 `flake.lock`，保持工作区干净；另外 `.github/workflows/flake-check.yml` 的 `schedule` 触发每天 03:40 先把 nixpkgs 刷到 master HEAD 再求值所有主机，赶在每周日 12:00 的 autoUpgrade 之前拦截上游回归（push/PR 触发只验已锁定的 `flake.lock`，看不到滚动通道的新提交）。
- **magpie 升级后 GUI 仍起来旧版本**：上游 `internal/gui/scheme_linux.go` 的 `registerScheme()` 把当时那个**绝对 store 路径**写进 `~/.local/share/applications/magpie.desktop` 的 `Exec=`（为抢占 `magpie://` 协议），且只在「已指向我自己」时跳过后写，于是升级后该文件仍指向旧版本，启动器与 `magpie://` 链接一直拉起旧版（CLI 走 PATH 故不受影响）。**现状**：`modules/home-manager/gui/apps/linux/utilities.nix` 用 `xdg.dataFile."applications/magpie.desktop"` 托管同一路径、每次 rebuild 按当前版本重写 `Exec=${pkgs.magpie}/bin/magpie`。**注意**不能用 `xdg.desktopEntries`——它写进 profile（`XDG_DATA_DIRS`），会被优先的 `XDG_DATA_HOME`（`~/.local/share`）旧文件盖掉。**移除条件**：上游不再把绝对路径钉进 `Exec`（或提供关闭自注册的开关）后。**同一根因第二处**：`magpie autostart on` 同样把 `os.Executable()` 绝对路径写进 `~/.config/autostart/magpie.desktop`，升级 GC 后开不了机自启；故自启也由 HM 声明（`xdg.autostart.entries`，同 `media.nix` 的 clash-verge 做法），`Exec=magpie tray` 走 PATH 恒指当前版本。
- **magpie 打开含 `<video>` 的页面（如插件 demo）时 WebKitWebProcess SIGABRT**（2026-11-22 定因）：WebKitGTK 给每个 `<video>`（静音的也算）建 audio sink，用 `autoaudiosink`（`gst-plugins-good` 的 `libgstautodetect.so`）；NixOS 下没有任何插件目录进环境，创建失败即 `MediaPlayerPrivateGStreamer::createAudioSink` 里 `RELEASE_ASSERT` abort，窗口留白。上游 `webkitPlaysVideo` 只在「找到 coreelements 却找不到 autodetect」时禁用视频，一个目录都看不到时反而误判可播。**现状**：`pkgs/magpie` 的 GUI 版把 gstreamer + gst-plugins-base/good 带进闭包，并在 package main 注入 init 写 `GST_PLUGIN_SYSTEM_PATH_1_0`；不用 shell wrapper，以免改掉 `os.Executable()` 破坏 magpie:// 条目。**移除条件**：Wails 提供 GST 插件路径接线，或 webkitgtk 包自带插件路径后。
- **Qt 应用在 niri 下没有标题栏**（2026-10-20）：`prefer-no-csd` 让 Qt6 的 `QWaylandXdgSurface::Toplevel::requestWindowFlags` 显式请求 server-side decoration，而 niri 永不画 SSD、Qt 又据「已请求 SSD」抑制 CSD，于是 Telegram/qView/VLC 全无边框（拿不到按钮）。**现状**：接受，不做 workaround —— 唯一能给 Qt 装回红绿灯的 `whitesur-qt-decoration` 未打包且是私有 ABI。**移除条件**：Qt 或 niri 支持「客户端装饰优先」协商，或上游提供可用的 Qt 装饰插件。
- **dalibre 的 Glance 书内预览不可用**（2026-11-09）：Glance 要 WebKitGTK **4.0**（`libwebkit2gtk-4.0.so.37` + `libjavascriptcoregtk-4.0.so.18`），nixpkgs 已随 libsoup-2.4 一并移除，4.1 的 soname 不同、ABI 不兼容，不能顶替。**现状**：该功能懒加载，缺失时只有 Glance 用不了，其余（书库浏览、元数据、编辑、OPDS、MCP）正常。**移除条件**：上游改用 WebKitGTK 4.1，或 nixpkgs 恢复 4.0 后，在 `pkgs/dalibre` 的 runtimeLibs 里补 `webkitgtk_4_0`。

- **SPICE 3D（`virtio-vga-gl` + `gl=on`）在本机 NVIDIA 专有驱动上必然黑屏，根因既不在客户机也不在设备 cgroup**（2026-10-28 定因）：客户机侧完全正常——`virtio_gpu` 带 `+virgl`，客户机 EGL renderer 报 `virgl (NVIDIA GeForce RTX 3060 Ti)`，niri 正常起 greeter 并选好 1280x800 模式，**黑屏全在宿主机的 SPICE 链路**，且两端各有一个独立的坑。① 服务端：SPICE 的 GL scanout 要把客户机 virgl 的 dma-buf 导进 QEMU 自己的 EGL 上下文，NVIDIA 专有 EGL 导不进来 → QEMU 侧打 `spice: cannot import memory object from fd` / `cannot create new texture from fd`，**display 通道根本不开**（客户端只走到 `main channel: opened` 就干等，窗口不映射，18 秒只烧 70ms CPU）；用无客户机的裸 QEMU（`-spice gl=on,rendernode=/dev/dri/renderD128`）复现同样报错、同样卡住，证明与客户机内容无关。② 客户端：spice-gtk 会崩，见下一条。实测矩阵（`virtio-vga-gl` 要求 QEMU 存在带 GL 的显示后端，libvirt 下只有 SPICE `gl=on` 算，于是「要 virgl 就必须开 SPICE GL」）：`-display egl-headless,gl=on` + SPICE `gl=off` 能让客户机用 virgl 正常渲染，但 console 的 surface 归 GL 所有，SPICE 2D 通道无内容可送（`screendump` 报 `no surface`）；`-display egl-headless,gl=on` + SPICE `gl=on` 被 QEMU 拒（`The console already has an OpenGL context`）；换普通 `virtio-vga` 时 SPICE 2D 正常（`screendump` 出 1280x800 图），但客户机 niri 拒绝软件渲染器（`software EGL renderers are skipped` → `no allocator available for device`），画面仍全黑。**因此 `modules/nixos/virtualization/default.nix` 里那段 `cgroup_device_acl` 不是解药**：本机 cgroup v2 上 libvirt 根本没挂 device BPF（QEMU scope 的 `cgroup.controllers` 里没有 `device`），ACL 形同虚设，客户机能用 virgl 是因为压根没被限制。**可行路径**：① 客户机内装 wayvnc 之类「在客户机内自己抓屏」的守护进程（niri 支持 screencopy，virgl 与 GPU 加速都保留，绕开 SPICE）；② 宿主改用 nouveau 等 Mesa 栈（Mesa 的 dma-buf 导入导出才与 virgl 兼容）；③ 加第二块显卡做 VFIO 直通；④ 客户机换成能接受 llvmpipe 的会话（普通 `virtio-vga` + 软件渲染的 sway/X11），此时客户端还要避开下一条的崩溃。**移除条件**：NVIDIA 专有 EGL 支持导入 virgl 的 dma-buf，或上游 libvirt/QEMU 提供不依赖 SPICE GL 的 virgl 帧回读。
