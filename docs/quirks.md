# 平台适配特殊处理（坑位清单）

每条只写「是什么 + 根因 + 移除条件 + 详见何处」，不超过 3 行；细节放对应源码注释或 `docs/` 里。

- **国内清华镜像源**：二进制替换源与 nixpkgs 源码均使用 `mirrors.tuna.tsinghua.edu.cn`。若身处境外，下载速度会偏慢，可自行更换镜像。
- **Pot 划词翻译的文本来源**：Pot 自带的 `/selection_translate` 读的是 PRIMARY 选区、不是剪贴板（两条独立通路；实测 Pot 的读取本身是新鲜的），所以「先复制、再按 Alt+T」会翻到上一次的选区内容。`pot-ctl selection`（`modules/home-manager/gui/apps/linux/pot.nix`）因此改为自己读 PRIMARY 选区、为空再退回剪贴板，再 POST 到 Pot 的 `/translate`；`Alt+X` 的 OCR 结果同样直接管道进 `pot-ctl translate`。**移除条件**：上游提供「指定文本」的热键/接口后，可去掉这层封装。
- **候选窗九宫格竖切线上的 1px 线**（**2026-10-22 已定位并修复**）：niri scale `1.5` 下候选窗右侧竖切线恒有 1 根欠覆盖的设备像素（卡片白 217、该列 177-182，亮度随背后窗口变 ⇒ 是漏底不是灰线；横切线干净）。**真凶是 GTK im module 的 client-side popover**——GTK4 应用（ghostty 等）在 `GTK_IM_MODULE=fcitx` 下由**应用进程自己**用 `gtk3/fcitxtheme.cpp` 的 `Theme::paint` 拼九宫格画候选窗，与 classicui / msime 插件无关（冻结应用进程画面即静止、`--disable classicui` 后 classicui 侧探针全零命中，均已实测）。**根因**：GTK 先把整块 paint 录制进 cairo recording surface（`gtk_snapshot_append_cairo`），1.5 倍缩放发生在回放阶段，录制上下文里 CTM 是单位阵、`device_scale=1.0`，所以「在 paint 里读缩放再按设备像素量化切线」拿不到真值（该方案已实现并真机实测无效，勿再走）。**修复**：`pkgs/fcitx5-gtk/nine-slice-overlap.patch`（经 `overlays/default.nix` 的 `fcitx5-gtk` override 生效）让相邻瓦片沿共享切线**重叠 1 逻辑像素** + `CAIRO_EXTEND_PAD`，不依赖读取缩放；九片改在 `cairo_push_group` 内用 `CAIRO_OPERATOR_SOURCE` 绘制、`alpha` 最后整体应用一次（否则半透明的高亮美术在重叠处叠两次 alpha 会出现 3 列亮带，复刻实测 102→153）。真机 A/B（同一批 10 组输入，仓库自建产物对照）：未打补丁 7/7 出缝（lum 169-170、`offR=9`），打补丁 **0/8** 出缝，且高亮行切口列回到与邻列同值（195 vs 175）；忠实复刻（recording + 1.5x 回放）50/100 宽度出缝 → **0/100**。**移除条件（2026-10-25 已执行）**：上游拒收等价修法（[PR #44](https://github.com/fcitx/fcitx5-gtk/pull/44)）；全局 `GTK_IM_MODULE` 移除后 Wayland 应用走 text-input-v3/classicui，ghostty/WPS/XIM 兜底三项手测通过，补丁与 fcitx5-gtk overlay 已删（X11 下 fcitx5-gtk 走 classicui-XCBUI 不经 popover 代码；若重新启用该路径需恢复补丁）。菜单窗（`[Menu/Background]`）走 `Theme::paint` 的 overlay 分支，本补丁只覆盖背景/高亮/箭头四类九宫格。
- **msime 0.13.0 的 notice 两表错位**（2026-10-22 定位，**2026-10-25 已随上游修复移除**）：上游 #9248 给 `MSIME_NOTICE_NAMES` 加了 `rime-wanxiang-CC-BY-4.0.txt` 却漏加 `MSIME_NOTICE_SOURCES`，`ZIP_LISTS` 装许可文件时整体错位一格，`frontend-npm-NOTICES.txt` 装不出来 → `msime-fcitx5` 的 `installCheckPhase` 断言失败；曾以 `pkgs/msime-fcitx5/notice-lists-alignment.patch`（经 `modules/nixos/core/default.nix` 的 overrideAttrs）补回对齐。**已移除**：上游已在 `platforms/linux/CMakeLists.txt` 自行补齐（msime master 2026-10-25），旧补丁反而造成 28/27 错位，补丁与目录已删。
- **msime 0.13.0 设置窗口前端编不出来（fileset 白名单漏文件）**（2026-10-25）：上游 da0e42f7 起 `packages/ui` import 了根目录的 `resources/keyboard-skin-presets.json`，但 `platforms/linux/nix/desktop.nix` 的前端 fileset 白名单没收录它——GitHub 源码树里文件在、构建树里没有 → vite `Module not found`，`msime-desktop-frontend` 失败并拖垮 `msime-fcitx5`。**现状**：`modules/nixos/core/default.nix` 经 `msime-fcitx5.override { settingsWindow = … }` 给 `msime-desktop` 换一层 `stdenvNoCC.mkDerivation` 包装，在 frontend 构建树里把该文件从完整输入源码补回。**移除条件**：上游修好 desktop.nix 的 fileset 后删 `msimeDesktopFixed` 段落。
- **WPS 中文输入失效（全局 IM 变量删除后）**：wpsoffice-cn 自带 Qt5（libQt5*Kso）与自带的 fcitx platforminputcontext 插件，该插件仅在 `QT_IM_MODULE=fcitx` 时被 Qt 加载；Qt5 无 XIM，`XMODIFIERS` 兜不住。**修复**：`productivity.nix` 用 `wrapQtXWayland`（`binaries=` 多入口）给 wps/et/wpp/wpspdf 注入。**移除条件**：恢复全局 `QT_IM_MODULE`，或 WPS 支持原生输入协议时。
- **NVIDIA 显存泄漏修复**：`modules/nixos/hardware/nvidia-base.nix` 配置 Niri 应用专属参数，限制空闲缓冲区池大小，规避显存泄漏问题。
- **显示器冷启动 EDID 自愈**：4K 屏长时间断电再上电时，NVIDIA 在 HPD 边沿立刻读 EDID，而该屏是「DP 接收端先起（1~3s 就拉高 HPD）、scaler/EDID 后起」，于是只读到合成 stub（`Nvidia 0x0000 Unknown`，模式列表只剩 640x480，叠加 scale 1.5 后逻辑 426x320）。stub 校验和有效且连接器仍 connected，RM 把显示对象连同 stub 一起缓存，只有**新的 HPD 边沿**或驱动重载才重建——`echo detect > status` 只刷新内核侧缓存，2026-09-26 实测 detect 每 2s 打满 10 分钟 + 两轮 force=off（链路真断）重训仍拿不回真 EDID，因此旧版 detect 自愈不可能生效；该屏还会拒绝 DDC/CI 软关机（VCP D6=0x04 → DDCRC_VERIFY，HPD 不撤销），所以也没法靠 DDC 逼它重初始化。`hosts/desktop/edid-reprobe.nix` 改为：检出 stub 且显示器 DDC 已就绪后，把本屏完整 EDID（`hosts/desktop/edid/icd-gx288ur.bin`，含 DisplayID 3840x2160@150）写进连接器 debugfs 的 `edid_override`——内核 7.2 起 override 不再让 probe 跳过 detect，nvidia-drm 每次 detect 都会把 override 交给 RM，连接器状态仍按真实 HPD 汇报，显示器断电即撤销 override。`drm.edid_firmware`/`video=` 已排除（冷启动时会把 4K 模式塞给尚未就绪的面板 → 黑屏）。完整根因与实测记录见该文件头部注释。
- **WinApps（Windows 应用接入桌面）**：libvirt 后端，接入层 `modules/home-manager/gui/desktop/linux/winapps.nix`，装机盘 `pkgs/windows-vm-media`（xorriso 往上游 ISO 追加，不重打包）。**密码不进 nix store**：`RDP_ASKPASS` 读本机 `~/.config/winapps/rdp-pass`（0600）。探针走 libvirt `<hostdev>` 直通而非 RDP，模块提供 `winapps-usb attach/detach <vid:pid>`「谁用谁拿」。**完整手册见 `docs/winapps.md`**。
  - 两个已知坑：本地化 Windows 上 RDP 放行必须走 `WINAPPS-SETUP.bat`（上游按英文组名放行在中文系统必然失败）；直通期间设备**仍出现在 `lsusb` 里**，别拿它判断归属，看 `/dev/ttyUSB*` 或 `winapps-usb`。
- **客户机使用宿主代理**：mihomo 只监听 `127.0.0.1`，客户机直接指向 `192.168.122.1:<port>` 会 `Connection refused`。`modules/nixos/networking/proxy-vm.nix` 的 `libvirt-proxy-forward.service`（`mySystem.proxy.exposeToVms`，desktop/laptop 已开）在 `virbr0` 地址上 socat 转发到回环端口——只暴露给客户机网段，且不必用 route_localnet + nftables DNAT 那套（会把回环地址变成可路由地址）。客户机侧仍需一次性把 WinINET 与 `netsh winhttp` 都指向 `192.168.122.1:<port>`，见 `docs/winapps.md` §10.4 / §12.5。
- **PSI / iowait 被 io_uring 虚高**（2026-10-23 定因）：内核按 `in_iowait` 记 iowait，而 io_uring 的 `io_cqring_wait` 把**等 timer/poll 的线程**也记成 io-wait，于是 `/proc/stat` 的 `iowait`/`procs_blocked` 与 `io.pressure` 整体虚高（本机常态 60%+、`procs_blocked` 恒等于等待线程数），但设备层 `%util=0`、该 cgroup `io.stat` 为空。A/B 实测：同一套等待线程，`IORING_ENTER_NO_IOWAIT` 置位 → 0%，不置位 → 100%。**现状**：ghostty 的 `async-backend` 改 `epoll`（`gui/apps/shared/ghostty.nix`），实测该 scope 的 `io.pressure` 由 60% 归零。**移除条件**：上游 liburing/libxev 默认带 `IORING_ENTER_NO_IOWAIT` 后恢复 `auto`。
- **自动升级固定走 flake**：`system.autoUpgrade.flake` 由 `networking.hostName` 推导出 `<primaryUser home>/Projects/nixos-config#<host>`（用户名经 `mySystem.primaryUser` 派生，不硬编码）。新增主机时 `networking.hostName` 必须与 flake 输出属性同名，否则 autoUpgrade 会找错目标。`allowReboot = false` 意味着内核更新后**不会自动重启**，需手动重启才能用上新内核。各主机的 flake 仓库统一位于 `~/Projects/nixos-config`，若某主机仓库路径不同需覆盖该选项。
- **滚动升级的可追溯性**：`--refresh` 每日重写工作区的 `flake.lock`，而 Nix 对脏 git 树令 `self.rev = null`，`system.configurationRevision`（`flake.nix` 中显式声明）会退化为 `"dirty"`，代际就无法回溯 commit。因此 `nixos-upgrade.service` 的 `postStop` 在升级成功后以本人身份提交 `flake.lock`，保持工作区干净；另外 `.github/workflows/flake-check.yml` 的 `schedule` 触发每天 03:40 先把 nixpkgs 刷到 master HEAD 再求值所有主机，赶在 04:40 的 autoUpgrade 之前拦截上游回归（push/PR 触发只验已锁定的 `flake.lock`，看不到滚动通道的新提交）。
- **magpie 升级后 GUI 仍起来旧版本**：上游 `internal/gui/scheme_linux.go` 的 `registerScheme()` 把当时那个**绝对 store 路径**写进 `~/.local/share/applications/magpie.desktop` 的 `Exec=`（为抢占 `magpie://` 协议），且只在「已指向我自己」时跳过后写，于是升级后该文件仍指向旧版本，启动器与 `magpie://` 链接一直拉起旧版（CLI 走 PATH 故不受影响）。**现状**：`modules/home-manager/gui/apps/linux/utilities.nix` 用 `xdg.dataFile."applications/magpie.desktop"` 托管同一路径、每次 rebuild 按当前版本重写 `Exec=${pkgs.magpie}/bin/magpie`。**注意**不能用 `xdg.desktopEntries`——它写进 profile（`XDG_DATA_DIRS`），会被优先的 `XDG_DATA_HOME`（`~/.local/share`）旧文件盖掉。**移除条件**：上游不再把绝对路径钉进 `Exec`（或提供关闭自注册的开关）后。**同一根因第二处**：`magpie autostart on` 同样把 `os.Executable()` 绝对路径写进 `~/.config/autostart/magpie.desktop`，升级 GC 后开不了机自启；故自启也由 HM 声明（`xdg.autostart.entries`，同 `media.nix` 的 clash-verge 做法），`Exec=magpie tray` 走 PATH 恒指当前版本。
- **Qt 应用在 niri 下没有标题栏**（2026-10-20）：`prefer-no-csd` 让 Qt6 的 `QWaylandXdgSurface::Toplevel::requestWindowFlags` 显式请求 server-side decoration，而 niri 永不画 SSD、Qt 又据「已请求 SSD」抑制 CSD，于是 Telegram/qView/VLC 全无边框（拿不到按钮）。**现状**：接受，不做 workaround —— 唯一能给 Qt 装回红绿灯的 `whitesur-qt-decoration` 未打包且是私有 ABI。**移除条件**：Qt 或 niri 支持「客户端装饰优先」协商，或上游提供可用的 Qt 装饰插件。
- **GTK4 应用启动时的三条 stderr 告警**（2026-10-20 查清）：`AdwTabBox reported min width -6` 与两条 `GtkImage baselines ... G_MININT` 来自 MacTahoe 主题的 `tabbar tabbox { margin: 0 -3px }` 与 `switch { font-size: 0 }`（字号 0 → 基线除法得 inf → int 成 G_MININT）；`vkAcquireNextImageKHR(): VK_ERROR_OUT_OF_DATE_KHR` 来自 GTK 4.22 默认 Vulkan 渲染器，`GDK_VK_CHECK` 对「窗口刚 map 需重建 swapchain」这个正常返回值也打告警，属上游噪音。**现状**：前两条由 `themes/variants.nix` 的 `gtk4UserCss` 末尾覆盖压掉；Vulkan 那条不动（除非全局 `GSK_RENDERER=gl`，代价是丢掉 Vulkan 路径）。**移除条件**：主题改掉这两条规则，或 GTK 不再把 OUT_OF_DATE 走告警宏。
- **Tern 官方安装包**（2026-10-19 起）：预编译二进制启动时 dlopen X11/Wayland/Vulkan 图形栈，nix-ld 默认集缺库即 panic（`failed to load libxcb`），且它会把**自身绝对路径**写进 `~/.local/share/applications/so.stencil.tern*.desktop`（绕过 wrapper 就丢库路径）。**现状**：`~/Apps/Tern/tern` wrapper 补 `LD_LIBRARY_PATH` 后 exec `tern-bin`（自更新只替换 `tern-bin`，wrapper 保留；nixpkgs 升级后按文件头注释重新生成库路径），`~/.config/tern/settings.json` 置 `"desktop_integration": false` 阻止自注册，桌面条目由 `modules/home-manager/gui/apps/linux/terminal.nix` 托管。**移除条件**：nixpkgs 收录 Tern 后。
- **babry 的 `save_dir` 配置要 0.1.4 才生效**（2026-10-20）：HM 早已声明 `~/.config/babry/config.toml`，但当时自维护的 `pkgs/babry` 锁在 0.1.1，该版本存盘路径写死 `XDG_PICTURES_DIR` / `$HOME/Pictures`、根本不读配置文件，于是 PNG 一直堆在 `~/Pictures` 根下。**现状**：已升到 0.1.4（`save_dir` 0.1.3 引入），wrapper 顺带补 `niri`（多显示器查询）与 `fontconfig`（`fc-match` 兜底字体），并因上游测试套件在沙箱过不了而 `doCheck = false`（上游 CI 也只 `cargo build`）。**移除条件**：上游测试可稳定通过后恢复 check。
- **微信窗口内光标退回原始箭头**（2026-10-20 查清）：微信 4.x 主窗口是 XWayland 上的 **Qt 5.15.14 静态链接**客户端，而 xwayland-satellite 的 XSETTINGS 只有 3 个整型键、**没有 `Gtk/CursorThemeName`**；Qt5 的 `QXcbCursor::createFontCursor` 于是把空字符串交给 `XcursorSetTheme()`，这条 X 连接的主题名被清空，libXcursor 回落到字面量 `default`，而 `XCURSOR_PATH` 里没有目录提供 `default/` → 全部 ENOENT → 用 X 核心字体光标（XFixes 实测 10×16、2 级 alpha；正常 Bibata 是 24×24、73 级 alpha）。**`XCURSOR_THEME` 对它无效**：该路径只认 XSETTINGS / `Xcursor.theme` / `default` 三档，改 env 不会有结果。**现状**：`themes/default.nix` 把 Bibata 整目录再软链一份成 `~/.local/share/icons/default`（HM 的 `xdg.dataFile`，无需改微信）；实测补上后同一窗口内光标恢复 24×24 抗锯齿。**移除条件**：xwayland-satellite 补写 `Gtk/CursorThemeName`（上游 [PR #423](https://github.com/Supreeeme/xwayland-satellite/pull/423) 方向）或微信改用 Wayland 后端后。
- **改用户名后 msime 状态里留着旧 home 的绝对路径**（2026-10-23）：`msime-client` 把词库/用户数据目录**以绝对路径写死**在 `runtime-options.json`（`resources` / `dictionaries` / `user_data` / `cache` / `preferences_directory`）与 `dictionary-updates/{loaded.json,installed.json,generations/*.json,verification/**}` 里。改名后这些路径仍指向旧 home：msime 启动时按记录路径 `mkdir` 失败于 `/home`（EACCES）⇒ 词典查询走空、`msime config` 报 `preferences storage failed: Permission denied`。**`msime-linux-prepare --refresh` 修不了**（它先按记录路径找词库，找不到即失败并原样保留）。**现状**：迁移 home 后把这些 JSON 里的旧路径整体替换成新路径（`grep -rl /home/<旧名> ~/.config/msime-client` 定位），再用 `msime-linux-setup --register` 重建用户单元。**移除条件**：上游改成按 `XDG_CONFIG_HOME` 现算路径（不再持久化绝对路径）后。
- **改用户名后 msime 的用户单元软链仍指向旧包版本**（2026-10-23）：`msime-linux-setup` 早期版本把 `msime-linux-{clipboard,online,voice}` 以**绝对 store 路径**软链进 `~/.config/systemd/user/`（含 `.wants` 目录）。包升级到 0.13.0 后这些软链仍指向 0.12.1 的 `ExecStart`，于是 `msime-linux-clipboard-monitor` 等进程跑的是旧二进制。**现状**：`systemctl --user disable` 后删掉这三条软链，再 `msime-linux-setup --register` 让新版本按 `/run/current-system/sw/share/systemd/user` 重新 `enable`（解析到当前系统的包路径）。**移除条件**：不再需要手动删——`--register` 已在 0.13.0 覆盖这一步。
- **改用户名会重建账户，不是改名**（2026-10-23）：`update-users-groups.pl` 的 `uid-map` / `declarative-users` 均按**用户名**索引，换名字即视为新用户——旧的会被删、新号从 1000 重新分配（1000 当时还被旧用户占着，实际会拿到 1001），`createHome` 在新路径建空目录，旧 home 连同属主成为孤儿；`auto-subuid-map` 同样按名索引，rootless 容器区间会挪到新段，podman 存储里按 100000 起始写的 uid 映射全部错位。**现状**：`mySystem.users.<主用户>` 用 `mkDefault` 钉死 `uid = 1000` 与 `subIdStart = 100000`，改名时数值身份不变；还须手动把 `/home/<旧名>` 迁到新路径并确认 `~/.config/git/config` 之类被 HM 接管的软链随重建刷新。**移除条件**：不需要——这是改名迁移的固定前置，新机器上留着也无害。
- **fontconfig 家族别名必须用 append，不能用 prepend**（2026-10-23 定因）：`modules/nixos/core/locale.nix` 原用 `mode="prepend" binding="strong"` 给 HarmonyOS Sans SC 挂 Noto 兜底，但 prepend 是把 Noto **插到最前**、把请求家族整个顶掉——实测 `fc-match "HarmonyOS Sans SC"` 返回 Noto Sans CJK SC，而 GTK 的 `gtk-font-name`、Noctalia 的 `font_family` 都写的是 HarmonyOS，于是界面全程在渲染 Noto 的拉丁字形。**现状**：改成 `mode="append" binding="weak"`（缺字才轮到 Noto，韩文仍能兜住）；**移除条件**：不需要，这是 fontconfig 语义的固定前置。
- **Ghostty 不读 fontconfig 的 hinting 设置**（2026-10-23）：ghostty 走自己的 FreeType 加载标志，默认 `hinting,no-force-autohint,no-monochrome,autohint,light`，系统侧 `hintstyle=none` 对它无效；而 `fonts.packages` 的 Maple Mono 特意选了 `-unhinted` 构建，autohint 会把那份刻意不 hinting 的轮廓重新对齐。**现状**：`gui/apps/shared/ghostty.nix` 显式设 `freetype-load-flags = no-hinting,...,no-autohint,no-light`。**移除条件**：不需要——该键对 macOS 无效（走 CoreText），写了无副作用。
- **emoji 彩色渲染走 `lang=und-zsye` 查询，`fc-match …charset=1F600` 返回 DejaVu 不代表实际渲染**（2026-10-23 定因）：fc-match 的 charset 排序会把带单色 emoji 轮廓的 DejaVu Sans 排在 Noto Color Emoji 之前；但 Pango/Chromium/Qt6 对 emoji 段落用 `lang=und-zsye` 查询，命中 60-generic.conf 的 color 偏好 → Noto Color Emoji（实测 pango-view 渲染为彩色）。实测给家族列表 append Noto Color Emoji（weak/strong）都纠正不了 charset 排序，strong 反而会把 ⚙ 等杂项符号也变彩 emoji。**现状**：不做 workaround。**移除条件**：不需要——fontconfig 匹配器固有打分行为，记录以免再试。
- **13600KF 混合架构下调度器对 P/E 无感：`cpu_capacity` 全 1024**（2026-10-23 定性）：双层原因，均不在配置层。① 上游设计：[intel_pstate 文档](https://docs.kernel.org/admin-guide/pm/intel_pstate.html) 的容量不对称调度默认只给**无 SMT** 的混合架构启用，hybrid+SMT（P 核带 HT）改走 ITMT 性能优先级路径（SMT 域与 `SD_ASYM_CPUCAPACITY` 互斥，两者共存的上游工作 7.3 才开始且只修到簇级负载均衡），而优先级同样取自各核的 highest HWP/CPPC 性能等级。② 固件堵死另一路：实测 B760-G（BIOS 1836）把所有核的 `acpi_cppc/highest_perf` 都报 255（P/E 无差别；`nominal_perf` 有 P=44/E=26 之分但内核容量路径不用它），于是容量与优先级双双全等，调度器把 20 个 CPU 当同质对待（APERF/MPERF 频率不变性仍正常，缺的只是放置层的 P/E 感知，属效率折损非故障）。**现状**：不做 workaround——`cpu_capacity` sysfs 只读（无 store 回调）、无对应 kernel 参数、`nosmt` 也不会让容量分化（固件 highest 全等）反损 6 线程；缓解仅 per-app：延迟敏感进程 `taskset -pc 0-11` 或 systemd `CPUAffinity`（P 核 cpu0-11、E 核 cpu12-19）。附：`core_id` 本就是稀疏编号（P={0,4,8,12,16,20}、E={24..31}），内核日志里 `likely on CPU 15 (core 27, socket 0)` 是**段错误打印的固定格式**（cpu15 的 core_id 就是 27），不是拓扑枚举错误。**移除条件**：BIOS 更新后 `cat /sys/devices/system/cpu/cpu{0,14}/acpi_cppc/highest_perf` 出现 P/E 区分，或上游合入 SMT+容量感知（届时 `cpu_capacity` 自行分化）。
- **ghostty 着色器动画勿设 `always`**（2026-10-23 定因）：`custom-shader-animation = "always"` 让**每个**打开的 surface 空闲时也按屏幕刷新率跑着色器循环（官方文档明示 "can become quite expensive"；desktop 4K@150Hz 实测 3 窗口常驻 ~6% 单核 + GPU），默认 `true` 只动画焦点终端，拖尾/粒子在正打字的窗口里效果不变。**现状**：`gui/apps/shared/ghostty.nix` 不设该键、回落默认。**移除条件**：不需要——除非愿意用空闲 CPU 换后台窗口的粒子效果。
